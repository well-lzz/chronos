# Chronos harness 设计与演进

Chronos 的领域能力仍是「授权范围内搜索，并把事实、发现和真实流量写入黑板」。Harness 负责让这个循环在长时间运行、模型故障和并发工具调用下保持可控。这里记录当前实现、边界和下一步验收标准。

## 借鉴与取舍

| 来源 | 可借鉴的机制 | Chronos 的落点 |
| --- | --- | --- |
| [Pi 的 compaction](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/compaction.md) 与 [sessions](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/sessions.md) | 历史可追溯，模型上下文按阈值缩短，溢出后重试 | 黑板与流量保存证据；逐事件 JSONL 保存完整对话；压缩只作用于模型的活动窗口 |
| [Codex agent loop](https://openai.com/index/unrolling-the-codex-agent-loop/) | 工具结果进入下一轮推理；上下文预算和溢出恢复属于执行循环 | 在请求前压缩；上下文长度错误时进一步缩短并重试一次；工具调用和结果严格配对 |
| [Claude 长任务 harness](https://www.anthropic.com/research/effective-harnesses-for-long-running-agents) | 长任务靠外化状态与可恢复的增量进展，而非无限延长单个提示词 | 黑板保存事实、发现和子目标；只有连续无进展才耗尽 `MAX_BUMPS` |

## 当前运行契约

1. **上下文**：每次模型请求前检查消息预算。压缩只在无未完成 tool call 的边界删掉旧回合；单回合过大时缩短历史正文。旧 tool call 参数若必须缩短，改成合法 JSON 占位符。模型返回 context length 错误时用更小预算再试一次。黑板摘要每个新回合重新注入，已验证与高危 Finding 必保。长期未活动且有显式 `from_ids` 血缘关系的低价值记录，可在后台压成带成员 ID 的 cold digest；提交前复查活跃度，原始记录始终保留。
2. **模型故障**：操作人员可为单个 executor 显式配置备用 profile 链。非流式调用尚未返回内容时，401/402/403/404 立即熔断主 profile，429/5xx/网络连续三次后熔断；冷却依次为 1/5/30 分钟并落盘。400 与任务取消不切换。无备用 profile 时，原有回合保留和退避行为继续生效。
3. **工具并发**：一组全为无 body 的 GET/HEAD 请求时，最多同时执行 3 个；结果按模型原始顺序回填。写黑板、提交 flag、Python、TCP 和混合调用依次执行。每回合最多执行 40 个工具调用，超额调用收到明确的未执行结果，保证消息配对。
4. **长任务**：`MAX_BUMPS` 是连续无新事实/发现的上限；发现新进展就重置计数。任务仍受墙钟预算约束。TCP 连接和读取响应任务取消，不再等待完整网络超时。Scope 锁仍在每次出网工具调用处生效。
5. **工具与操作员输入**：操作员消息进入所选执行器的原会话。Scope 变更会取消并等待旧运行结束，再创建独立运行 ID、会话、黑板与流量日志。工具在执行前先受 Scope 硬锁约束，再匹配可选 allow/deny/ask 规则；ask 等待操作员在控制台逐次批准，超时拒绝，结果明确标注平台管控而非目标防御。
6. **跨进程恢复**：每个 mission/executor 的消息、排队指令和压缩快照追加到私有权限的 `sessions/` JSONL。重启时仅恢复同一运行 ID 的窗口；崩溃时未完成的 tool call 收到“结果未知”占位结果，不自动重放任何工具。末尾损坏的半条记录会被舍弃。日志保留完整历史，可能包含目标返回的敏感内容，应按证据日志一样管理。
7. **计量与归档**：每次实际 LLM 请求均写轻量用量行；只有 `LLM_RECORD=1` 才保存完整消息与响应。任务结束时报告、黑板和流量可打成按 SHA-256 去重的可移植归档；可选 webhook 对高危发现与自然完成事件做一次性通知。

## 仍需完成的能力

以下是下一阶段的独立工作，不把它们伪装成现有能力：

- **恢复覆盖率**：当前有未完成 tool call 与 JSONL 半条记录的测试；还需进程级崩溃注入、跨版本日志迁移及日志保留/清理策略。
- **可托管的长进程**：若未来需要后台脚本，应提供 start/status/cancel/reap 生命周期、并发配额和操作系统级隔离。当前 `run_python` 是最多 60 秒的同步工具，且默认关闭。
- **可观测性与评估**：请求用量、延迟、状态和可选完整记录已经可查；工具排队时长、并发峰值与发现率仍需加入统一评测。用同一批授权离线任务做 A/B 对照，以单位 token 的验证发现数、完成率和恢复成功率判定收益。
- **并发策略**：当前平台任务并发上限仍是 3。跨任务队列的公平性、背压和全局模型请求限速需要用实际负载数据设计，不能把并发数简单调大。
