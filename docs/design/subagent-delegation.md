# 子 Agent 委派：作为上下文管理策略

> **状态（2026-10-30 核对）**：本方案已实现：有界子任务委派与续跑见提交 `4a37269`（`internal/solver` 中的 `delegate` 工具）。 本文保留设计取舍记录，实现细节以代码为准。

> 设计基线文档（纯设计，不含实现）。承接 `docs/mission-modes.md` 的「任务=搜索」与现有 `solver` / `swarm` / `blackboard` / `scope` 内核。
> 目的：给 Chronos 增加一条它现在**没有**的轴——让一个 executor 把一块有界的子调查**委派**进隔离上下文，用完即弃，从而在**无损**的前提下控制父 executor 的上下文增长。

---

## 0. 为什么要做（它补的是哪个洞）

Chronos 当前的上下文管理只有两条路径：

1. **单条不断增长的 transcript + `compaction.go` 压缩**——有损、事后补救。
2. **黑板 `Summary()` 每 cycle 重注入**——保真，但受 recency cap 截断。

**缺的是第三条**：Claude Agent SDK 式的「把一块发散工作塞进隔离子窗口、只回传精简结果」的**事前预防**路径。它的价值在于：父 executor 遇到「要深挖一大块（一个端点、一个协议、一份固件）」时，不必让这些几十次工具往返污染自己的主窗口，而是**外包给一个隔离子 Agent**，自己只拿回一条结论。

这与 Chronos「模型自身 agentic 推理决定成绩」的信念一致：委派是**模型管理自己上下文**的工具，不是预设的侦察/利用分工。

### 与设计哲学的自洽（重要）

README 明写 `无任务角色分解`。委派是一种分解，必须守住两条边界才不破坏「0 剧本」：

1. **由模型临场决定**何时、委派什么——不是硬编码管线。
2. **子 Agent 用同一份中性契约 prompt**——不塞专门的攻击角色/剧本。

委派在这里是「上下文策略」，不是「分工流水线」。

---

## 1. 一句话形态

给 executor 增加一个 `delegate` 工具。模型调用时，harness 开一个**临时子 Solver**：

- **全新消息窗口**（不继承父 transcript）；
- **继承**父的 scope（可收窄、永不扩大）、**共享**同一块 `blackboard` / `traffic.Log` / `*Tokens`；
- 子 Agent 像普通 executor 一样把 Fact/Finding **写进共享黑板**；
- 结束时**只把一行摘要 + 新建的 finding/fact ID 列表**作为一条 `tool_result` 回给父。

父窗口只增长这一条结果，**与子 Agent 实际干了多少活无关**——这就是「省上下文」的本质。

---

## 2. 关键决策（已拍板）

| 维度 | 决策 | 理由摘要 |
|---|---|---|
| **触发方** | **模型自主调 `delegate` 工具** | 这才是真正的「模型自主上下文策略」，贴合 Chronos 信念；非 harness 自动 |
| **回传通道** | **写黑板 + 回传 finding/fact ID** | 发现持久、swarm 兄弟与报告立即可见、`evidence_refs` 保持有效；父上下文只长一行；免疫逐层再压缩的 context loss |
| **深度** | **默认 1，env 可调至 2（仅 killchain），永不无界** | 目的是上下文管理而非深度分解；默认扁平；深度 1 结构性消灭 fork bomb | 
| **叶子 spawn** | **叶子永不持有 `delegate` 工具**（不可协商） | 各家公认硬规则（Claude 第 5 层撤工具、Codex 子代理即叶子） |
| **失败/超时** | **父可 `resume` 子 Agent 接着跑** | 比「一次性丢弃」更强；深度 1 下语义最干净、最易实现 |

## 3. `delegate` 工具契约（概念层）

**入参**

- `task`（必填）：子 Agent 的**唯一上下文**。父看不到的东西都要写进这段字符串——目标描述、已知事实、要查什么、已排除什么。
- `max_steps`（必填）：子 Agent 自己的步数小预算（从父剩余预算里切）。
- `focus`（可选）：scope 的**子集**提示，仅用于收窄注意力，**越界即拒**。

**返回给父的 `tool_result`（精简、定长）**

```
{
  "status": "completed" | "inconclusive" | "stopped",
  "summary": "≤N 字的结论",
  "finding_ids": ["F7", "F8"],
  "facts_added": 3,
  "agent_id": "<子 Agent 句柄，用于 resume>",
  "stopped_reason": "max_steps" | "deadline" | "done" | ...
}
```

**不包含**子 Agent 的任何工具往返明细。父若要看细节，去黑板按 ID 查，或 resume。

### 3.1 何时委派：给模型的判据

触发方是**模型自主**，所以「何时委派」不是 harness 写死的条件，而是写进 `delegate` 工具描述（加一点 prompt 引导）、由模型临场判断的**判据**。判据必须**完全围绕「上下文经济学」**，不围绕「攻击步骤」——后者会退化成剧本，破坏 `0 剧本` 原则。

**该委派的信号（满足其一即值得）**

1. **有界、自包含的子调查**，会产生大量中间工具往返，但结论能压成几条 finding。典型：「把**这一个**端点/服务/协议彻底摸清并回报结果」「解析这份大文件、把结构映射出来」。父只要结论，不需要那几十次往返留在自己窗口。
2. **预判这块深挖会显著撑大父窗口，但只有结论对主线有用**——最核心的触发点。委派的本质就是「把注定污染主窗口的发散工作关进隔离窗口」。
3. **多个相互独立的子问题**，可并行各开一个子 Agent（受每父并发上限约束），父拿回多条结论汇聚。
4. **会产生超长工具输出**（大响应体、大 dump）的探查——原始输出不必常驻父上下文，让子 Agent 消化掉只回传提炼结果（原文仍在 traffic 日志可查）。

**不该委派的信号（反例，同样写进工具描述）**

- **一两步就能完成的轻量查询**：子 Agent 的固定开销（全新窗口 + 系统提示）不值。
- **严重依赖父当前上下文的工作**：子 Agent 只能通过 `task` 字符串拿上下文，传不全就会重复探索，反而更费——留在父自己做。
- **主线推理本身**：委派的是「支线深挖」，不是把整个 mission 甩出去。
- **已在 scope 边缘、靠收窄 focus 也救不回的**：委派不能扩 scope，越界直接拒。

**可操作的浓缩判断式（可直接作为工具描述的核心句）**

> 当你预见「接下来这段探查会产生远多于其结论价值的中间内容」时，委派它；当结论本身就是你下一步要用的东西、或离不开你现在的上下文时，自己做。

**重要**：以上是「引导」不是「保证」。和 Claude SDK 一样，模型可能用得不好（该委派不委派 / 过度委派——Claude 文档专门提到 Opus 5「过于积极地 spawn」需护栏勒住）。所以判据管「用得好」、§5 的机械护栏（深度/并发/子预算/全局预算）管「不失控」，两者缺一不可。§9 的委派树上线后，可从真实运行里观察「模型在什么情况下委派、划不划算」，反过来迭代这里的判据——优于一开始就把判据写死。

## 4. 子 Agent 生命周期

1. **spawn**：父模型调 `delegate` → harness 新建子 `Solver`：
   - `messages = [子系统提示]`（全新，**不继承父历史**）；
   - 子系统提示 = **同一份中性契约 prompt**（`BuildHeadlessPrompt` 复用）+ `task` + 继承的 scope 描述 + 「把发现写黑板，结束回报简要结论」；
   - 注入**同一个** `*blackboard.Blackboard`、`*traffic.Log`、`*Tokens`、`scope` 快照；
   - **叶子**（已达深度上限）构建工具集时**排除 `delegate`**。
2. **run**：子 Agent 跑自己的 tool loop，直到不再调工具 / 撞 `max_steps` / 墙钟片用尽 / ctx 取消。期间 `add_fact` / `add_finding` / `verify_finding` 直接落**共享**黑板；`http_request` / `tcp_send` / `run_python` 受**同一 scope lock**。
3. **return**：用黑板修订号差分（见 §6）算出本次子 Agent 新建的 ID → 生成一行摘要 → 作为 `tool_result` 回父。
   - 若 `status != completed`：**不销毁**子 Solver，持久化其状态以备 resume（见 §7）；
   - 若 `status == completed`：可销毁（或保留句柄一个 TTL 供追问）。
4. **父继续**：父下一步的 `bb.Summary()` 立刻能看到这些新 finding（同一块黑板），`tool_result` 里的 ID 让它能精确引用。

## 5. 机械护栏（贴合既有风格）

| 护栏 | 作用 | 对标 |
|---|---|---|
| **depth 上限** `MAX_DELEGATE_DEPTH` | 默认 1，上限 2；叶子撤 `delegate` | Claude 硬顶 5 撤工具 / Codex 默认 1 |
| **每父并发子** | 一个父同时最多几个在跑的子 Agent | openclaw `maxChildrenPerAgent` |
| **子预算** | 每子 Agent 的 step / 墙钟片，从父剩余切 | 现有墙钟 / `MAX_BUMPS` 思路 |
| **mission 预算** | 子 Agent token 走共享 `*Tokens`，**自动计入全局预算** | 现成，无需新增 |
| **scope 不可扩** | 子只继承或收窄，永不扩大 | 现有 scope lock 铁律 |

**子预算切分（决策）**：采用**「模型传 `max_steps` + harness 强制钳住」**。模型自己提 `max_steps`，但 harness 把它钳到硬上限——**≤ 父剩余预算的某比例（默认 50%）且不超过一个绝对步数上限**，取两者更小。这样既保留模型自主（它最懂这块该投多少），又用机械护栏杜绝「一个父把全部预算喂给单个子」。钳制发生在 harness 层，模型传多大都越不过。

**并发子 vs 全局预算（决策）**：子 Agent token 照旧走共享 `*Tokens`、**自动计入全局预算**；在此之上，把现有「预算告急即停开新题」那套 `MIN_REMAINING_SECONDS_TO_SPAWN` 闸门**复用到 `delegate` 的 spawn 准入**——当全局预算低于阈值时，**`delegate` 调用被拒，父改为内联自做**(tool_result 返回「预算不足，未委派，请自行处理」)。这样多子并发不会在预算告急时继续加速烧钱，且无需新增独立预算池。

## 6. 新增小基建：黑板修订号

为「结束时精确算出子 Agent 新建了哪些 ID」，黑板需要一个**单调递增修订号 / 游标**：

- 子 Agent 启动时记下起点 `rev0`；
- 结束时取黑板中 `rev > rev0` 的新 Fact/Finding ID 即为其产物。

**复用价值**：这个修订号顺带解决 swarm 的「cycle 内增量注入」（P5）——executor 记住上次见到的 `rev`，只在有新增时补注入增量，让兄弟协作接近实时。一处基建、两处受益，值得先建。

---

## 7. resume 机制（父可续跑子 Agent）

**目标**：子 Agent 撞 `max_steps` / 墙钟片没出结论时，父能让它**接着原上下文**跑，而不是丢弃重来。

**需要的持久化**（子 Solver 状态）：

- 子 Agent 的**消息窗口**（它自己的 transcript，含 compaction 后状态）；
- 它的**黑板起点修订号** `rev0`（resume 后继续差分）；
- 它的 scope 快照、剩余预算、`agent_id`。

**父侧契约**：`tool_result` 里带 `agent_id`；父模型可调 `delegate_resume(agent_id, extra_steps, note?)` 让该子 Agent 在原窗口继续，`note` 作为新的一条 user 消息注入（相当于父对子的追加指导）。

**为什么默认深度 1 让 resume 最简单**：depth 1 下父 resume 的永远是**自己的直接叶子**，一对一、无歧义。一旦 depth 2，「谁 resume 谁、祖父能否 resume 孙子」立刻复杂化——这也是默认 1 的又一理由。深度放到 2 时，resume 仅限**直接父子**，不跨层。

**持久化范围（决策）**：子 Solver 状态落盘到 **`CHRONOS_STATE_DIR/subagents/<mission>/<agent_id>/`**（与 `blackboards/`、`traffic/`、`reports/` 同级，顺带可观测）。**v1 只支持同进程 resume**——活进程里按 `agent_id` 索引内存中的子 Solver 对象即可 resume；落盘主要用于崩溃排查与审计。**跨进程崩溃恢复**（重启后从磁盘重建子 Agent 继续跑）**不在 v1 范围**，留到 engagement 长程场景确有需要时再做（活的 Solver 持有 client/ctx 不可序列化，重建需额外的 rehydrate 逻辑）。

## 8. 与现有三套机制的组合

- **与 compaction**：委派是**事前预防**（把发散工作关进隔离窗口），compaction 是**事后有损补救**。有了 `delegate`，父遇到「要深挖一大块」时**优先委派而非等压缩**——正好补上现在缺的「无损省上下文」路径。
- **与黑板**：选定的「写黑板」回传让子产物**天然持久 + 对兄弟和报告立即可见 + `evidence_refs` 不失效**，且**免疫逐层再压缩的 context loss**（产物不经摘要链，直接落同一块板）。这是比 Claude 纯摘要回传更强的一点，务必保留。
- **与 swarm**：子 Agent 是**某个 executor 的临时子代、用完即焚**，**不进 swarm、不占 peer 名额**。swarm 的「对等常驻协作」那条轴不动。两条轴正交：swarm = 横向协作覆盖；delegate = 纵向上下文外包。

## 9. 可观测性（别重蹈 swarm 共享「看不见」的覆辙）

控制台应显式展示**委派树**，否则又会「发生了但感知不到」：

- 父流里打一条 `⇲ delegated: <task 摘要>`；
- 子 Agent 有自己**可展开的子流**（复用现有 per-executor activity ring 思路，带 `parent` 关联）；
- 返回时父流打 `⇱ returned: [F7,F8] +3 facts (inconclusive)`；
- resume 时打 `↻ resumed <agent_id>`。

**子 Agent 的 `notify`（决策）**：子 Agent 调 `notify` 时，消息**进日志 + 显示在控制台该子 Agent 的子流里**（在委派树里可见），但**不注入父上下文**——父只在子 Agent 结束时拿到那条最终 `tool_result`。这与「只有最终结果回传给父」一致，既让操作员实时看得到子 Agent 的状态/阻塞，又不污染父窗口。

方法论硬规则：**深度 ≥3 必须先有 correlation ID + 嵌套 trace 才能跑**——这也是我们把上限压在 2 的原因之一（不触发这条重型要求）。

## 10. 深度决策的调研依据

| 框架 | 深度策略 | 关键细节 |
|---|---|---|
| **OpenAI Codex** | `agents.max_depth` 默认 **1** | 最克制，子代理即叶子 |
| **Claude Code** | 硬顶 **5** | 第 5 层叶子**自动失去 Agent 工具** |
| **openclaw** | 默认 `maxSpawnDepth=5`（1–5） | 另加 `maxChildrenPerAgent`(5) + `maxConcurrent`(8) |
| **Cursor SDK** | 无限制 | 实测被抱怨不可靠 |
| **agentpatterns.ai（方法论）** | 不设统一上限，**默认扁平 fan-out**，仅问题树真分层时用深度 | — |

**必须警惕的失败模式**：

1. **Re-dispatch 死循环 = fork bomb**：子工具与父重叠时只转发不干活。真实案例 opencode #18100：47 session 跨 20 层，第 2–18 层纯转发。→ 由「叶子撤 `delegate`」结构性消灭。
2. **逐层再压缩 context loss**：→ 由「写黑板」回传免疫。
3. **成本爆炸**：深度 3×分支 3 ≈ 比单层多一个数量级 token。→ 由「默认 1、上限 2」控制。
4. **可观测性**：深度 3 分支 3 = 13 session，需 correlation ID + 嵌套 trace。→ 上限 2 规避该要求。

**结论**：目的是上下文管理而非深度分解 → **默认扁平（深度 1）** 已拿到几乎全部收益；留 env 口子到 2 仅为 killchain；越过 2 收益递减而失败模式陡增，不开放。

## 11. 落地顺序建议（将来动手时）

1. **黑板修订号**（§6）——其它一切的前置，且复用到 swarm 增量注入。
2. **`delegate` 工具 + 子 Solver 生命周期**（§3/§4），深度锁死 1、叶子撤工具、写黑板回传 ID。
3. **机械护栏**（§5）——并发、子预算、深度 env。
4. **可观测性**（§9）——委派树展示，与功能同批上，别后补。
5. **resume**（§7）——子 Solver 持久化 + `delegate_resume`。
6. **（可选）深度 2**——仅在 killchain 验证 1 足够稳之后再开。
